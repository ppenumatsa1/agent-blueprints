Specification repository

Document-first requirements, without blocking the prototype.

A transcript or recording becomes a draft PRD immediately. A targeted “grill me” pass flags only the decisions that matter. The technical blueprint is designed separately, then both converge into executable work packages.

Business spec · what and why

  1. Extract problem, users, jobs to be done, and current workflow.
  2. Draft desired outcome, scope, stories, and business rules.
  3. Label each fact Confirmed / Assumed / Unknown / Out of scope.
  4. Prioritize questions that change correctness, safety, or architecture.
  5. Generate acceptance criteria and UAT scenarios.
Document first → clarify second

Technical spec · how

  1. Choose agent, API, or web app profile.
  2. Select implementation framework, language, runtime, hosting.
  3. Define interfaces, API contracts, state/data model, security boundaries.
  4. Apply local/Azure golden path, infrastructure, monitoring.
  5. Check compatibility and record deviations from defaults.
Blueprint independent of PRD

Third artifact: verification contract

Each requirement receives a stable ID and a measurable check before implementation. This is a proposed project convention—not a native Copilot feature.

REQ-001 Invoice > $10,000 requires approval Success: no payment without valid authorization Failure: payment tool invoked without approval Test: submit a $12,000 unapproved invoice Evidence: integration test + audit/payment-call trace Gate: critical; must pass for release

The coding agent reads the criteria. CI runs the actual tests. Missing evidence is unverified, never passed.

When can implementation begin?

Prototype gate: problem, primary workflow, high-risk constraints, and demo success criteria are explicit; lower-risk unknowns may remain labeled assumptions. Production gate: critical assumptions resolved and required acceptance tests, security, operations, and customer decisions evidenced.

Agent responsibilities

Instructions · Tools · Skills · Identity · State · Memory when needed · Observability · Eval datasets · Recovery · Tool authorization

Hosting

Preferred: Foundry hosted/managed agents where compatibility is confirmed. Otherwise containerized Azure hosting is an explicit exception. A framework, a harness, and a hosting service are different architectural layers.

App + API blueprint family

Two product compositions; three backend technology profiles.

API-only

Python/FastAPI · Node/TypeScript/Express · .NET/ASP.NET Core. OpenAPI, auth, persistence, tests and deployment included.

Web app

React frontend + separately deployable API + PostgreSQL. Do not enable agent-execution fields for a conventional web app or API.

Default deployment

Local: frontend, backend and PostgreSQL each containerized with Docker Compose. Azure: React and backend on ACA; Azure Database for PostgreSQL Flexible Server, low-cost Burstable baseline; Bicep infrastructure.

Work package contract

Work ID, objective, input requirement IDs, allowed files/interfaces, dependencies, acceptance tests, execution budget, evidence locations, and escalation triggers. A failed check triggers a bounded repair loop, never a silent exception.

Production operations built into templates

Entra authentication and least privilege; secrets managed outside code; secure API boundaries; health and readiness endpoints; structured logs, OTel, Application Insights, Log Analytics; retries/timeouts; configuration, environment separation, backup/restore and rollback planning; GitHub Actions CI/CD.

Verification and readiness

Don't trust generated code. Trust traceable evidence.

We reuse existing Copilot, GitHub Actions, and framework testing capabilities. A verification contract links each business requirement to tests and observable evidence.

Common tests · all projects

  • Unit, contract, integration, end-to-end
  • Authentication, authorization, boundary testing
  • Performance / resilience / deployment smoke tests as applicable
  • GitHub-native CodeQL, Dependabot, secret scanning and protection where available/configured
  • Review security-sensitive or insufficiently verified changes

Agent-specific evaluation

  • Task-success and business-outcome evaluation
  • Tool selection and tool authorization
  • Trajectory/workflow and recovery
  • Prompt injection and exfiltration attempts
  • Stochastic regression runs with calibrated thresholds
  • Human evaluation for subjective or high-stakes outcomes

Two readiness gates

GateRequired evidenceOutcome
PrototypeCore demo journey, critical negative cases, basic security, documented assumptions, preview + screenshots/videoDemonstrable, not production approved

Guardrail: Builders cannot weaken release criteria or approve their own failures. Protect contract files and CI settings with branch protections, required checks, and human review as appropriate.
What evidence is retained?

Requirement IDs → linked design → commits/PRs → test IDs → CI runs, trace/eval artifacts, screenshots/videos, residual risks, and approval decisions. Coverage gaps are explicitly labeled unverified.

Implementation sequence (proposed)

  1. Review and approve architecture: repo boundaries, common standards, agent profiles, compatibility assumptions.
  2. Define production-readiness contract: mandatory vs optional checks and evidence schemas for two blueprint families.
  3. Build the Spec Studio repo: transcript ingestion, document-first PRD, technical spec, verification contract, work-package export.
  4. Build the two blueprint repos: reusable paths, CI quality gates, local and Azure deployment templates using Copilot app.
  5. Audit and upgrade existing MAF/LangGraph projects: compare to readiness contract; close gaps rather than recreate functionality.
  6. Run a real customer pilot: first-call notes → 2–3 hour target demo, video/screenshots, measurable outcomes, feedback.

Key unresolved decisions

Foundry compatibility matrix

Confirm each framework and harness path's supported package/runtime lifecycle, tool hosting and state boundaries against current Foundry agent hosting offerings before promising one-click deployment.

Minimum production security baseline

Specify the public-repository GitHub security features actually available to the selected org/plan, and identify controls that must be implemented in application code or Azure rather than via scanning.

Verification schema and independent ownership

Decide schema/versioning, which checks are blocking, how the independent verifier operates, and who can approve changes to the contract or exceptions.

Prototype media capture

Choose a browser automation or screen recording approach that can capture a valid demo, mask sensitive content, and attach artifacts without claiming the UI was verified when it wasn't.
